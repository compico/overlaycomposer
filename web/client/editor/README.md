# Редактор: структура клиента

Цель — чтобы редактор можно было постепенно перевести на фреймворк (React/Svelte/Vue), не переписывая логику.
Поэтому код делится на слои, и **логика не знает про DOM**.

```
web/shared/            чистая логика без DOM и сети (types, geometry, history, snap) — тесты node:test
editor/lib/store.ts    реактивное хранилище: get / set / update / subscribe (контракт совпадает со Svelte store,
                       годится для React useSyncExternalStore и Vue shallowRef)
editor/lib/api.ts      тип `Api` (функция-запрос) и реальный `httpApi`; в тестах подставляется фейк
editor/lib/ui.ts       тип `Ui` {toast, fail} — что представлению нужно от окружения
editor/lib/dom.ts      $ и el — помощники ванильных представлений
editor/features/<имя>/
    model.ts           состояние в Store + действия; зависит только от `Api`; интерфейс — `XModel`
    view.ts            ванильный DOM: mountX(refs, model, ports); refs — элементы, ports — всё остальное снаружи
    model.test.ts      тесты модели с фейковым `Api`
editor/main.ts         «склейка»: общее состояние layout, канвас, панели, которые ещё не вынесены
```

## Правила

1. **Модель** (`model.ts`) не импортирует DOM, `fetch`, `window`. Всё внешнее приходит параметрами (`Api`, другие модели).
2. **Представление** получает модель и *утиные* «порты» (маленькие интерфейсы: `Ui`, `openStore()` …), а не обращается к глобальным функциям `main.ts`. Так его можно заменить компонентом, не трогая модель.
3. Зависимости между фичами — через интерфейсы моделей/портов, не через общие переменные модуля.
4. Новая фича — сразу в `features/<имя>/` по этой схеме; при правке старого кода из `main.ts` стоит выносить его туда же.

## Переход на фреймворк (как это выглядит)

Для каждой фичи пишется компонент, который читает `model` (`useSyncExternalStore(model.subscribe, model.get)` в React,
`$model` в Svelte) и вызывает его действия; `model.ts` остаётся без изменений вместе с тестами. Старое `view.ts` удаляется.
Переносить можно по одной фиче: ванильные и фреймворк-представления спокойно живут вместе.

## Что уже вынесено

- `notifications` — центр уведомлений (model + view + тесты модели).
- Инфраструктура `lib/` (store, api, ui, dom) и чистая логика в `web/shared/` (history, snap, geometry), которая и раньше не зависела от DOM.

## Что НЕ перенесено (всё ещё в `main.ts`, ~1970 строк)

Разделы `main.ts` в порядке файла; «Сложность» — оценка работы по выносу в `features/<имя>/`.

| Раздел | Строк | Что внутри | Что мешает вынести | Сложность |
|---|---:|---|---|---|
| state | ~20 | глобальные `layout`, `sources`, `selectedId`, `dirty`, `k` … | это и есть общее состояние: нужна модель `editor` (Store), от которой зависят остальные | средняя |
| helpers | ~30 | `toast`, `fail`, `markDirty`, `sourceOf`, `objName` | `toast` завязан на DOM (`#toast`), `markDirty` — на историю и бейджи | низкая |
| layout mode and snapping | ~40 | настройки Layout/Snap (localStorage), цели прилипания, рисование направляющих | настройки — это маленькая модель; рисование направляющих — часть канваса | низкая |
| history of edits | ~80 | запись/отмена/повтор (`History` из shared), кнопки ↶ ↷ | вызывает `refreshAll()` и читает `layout`: нужна модель layout | средняя |
| loading | ~45 | загрузка sources/layouts/plugins, `openLayout`, `init` | то же: пишет в общие переменные | средняя |
| rendering (канвас) | ~290 | рамки, ручки, перетаскивание, ресайз, обрезка, поворот, hit-test | самый плотный DOM+события; логику жестов можно оставить vanilla (в фреймворке канвас обычно остаётся императивным) | высокая |
| selection | ~15 | `select()` | перерисовывает три панели напрямую | низкая |
| layouts panel | ~65 | список layout, создать/дублировать/удалить, default | зависит от модели layout | средняя |
| layers panel | ~95 | слои, порядок, видимость/блокировка, переименование | зависит от модели layout и выбора | средняя |
| copy between layouts | ~80 | Ctrl+C/V между layout, диалог, связанные копии | зависит от модели layout и `save()` | средняя |
| add source | ~70 | диалог «Add Source» (вкладки, Twitch-ссылки, existing source) | много DOM; логика создания source/слоя | средняя |
| plugin store | ~210 | каталог, источники, токен GitHub, установка/удаление | чистый API-клиент + DOM: **лучший следующий кандидат** | низкая–средняя |
| properties panel | ~20 | контейнер панели свойств | зависит от выбора и layout | низкая |
| plugin settings form | ~290 | форма настроек плагина (все типы полей), права, сохранение | много DOM, но логика локальная | средняя |
| привязка layout к сценам OBS | ~50 | чипы сцен, «Add scene», конфликт привязок | зависит от модели layout и списка сцен OBS | низкая |
| settings (config.json) | ~330 | Settings: сервер, OBS, Twitch-аккаунты, устройства, автозапуск, импорт | крупнейший отдельный блок, уже почти независим — несколько features | средняя |
| import scene from OBS | ~50 | диалог импорта | небольшая модель + view | низкая |
| save | ~20 | Ctrl+S, PUT layout | зависит от модели layout и истории | низкая |
| keyboard | ~55 | горячие клавиши (Ctrl+S/Z/Y/C/V, стрелки, Delete, L) | диспетчер, который знает все действия; станет «командами» | средняя |
| websocket | ~80 | `/ws`: сцена, OBS-статус, обновления layout/sources | вызывает рендер напрямую; станет источником событий для моделей | средняя |

Порядок, который я бы рекомендовал: `plugin store` → `settings` (по частям) → `import` и привязка сцен → общая модель
`editor` (state + loading + save + history) → панели Layouts/Layers/Properties → keyboard/websocket как команды и события →
канвас последним (его разумно оставить императивным даже при фреймворке).
