# Редактор: структура клиента

Цель — чтобы редактор можно было постепенно перевести на фреймворк (React/Svelte/Vue), не переписывая логику.
Поэтому код делится на слои, и **логика не знает про DOM**.

```
web/shared/            чистая логика без DOM и сети (types, geometry, history, snap) — тесты node:test
editor/lib/store.ts    реактивное хранилище: get / set / update / subscribe (контракт совпадает со Svelte store,
                       годится для React useSyncExternalStore и Vue shallowRef)
editor/lib/api.ts      тип `Api` (функция-запрос) и реальный `httpApi`; в тестах подставляется фейк
editor/lib/ui.ts       тип `Ui` {toast, fail} — что представлению нужно от окружения
editor/lib/dom.ts      $ и el — помощники ванильных представлений
editor/features/<имя>/
    model.ts           состояние в Store + действия; зависит только от `Api`; интерфейс — `XModel`
    view.ts            ванильный DOM: mountX(refs, model, ports); refs — элементы, ports — всё остальное снаружи
    model.test.ts      тесты модели с фейковым `Api`
editor/main.ts         «склейка»: общее состояние layout, канвас, панели, которые ещё не вынесены
```

## Правила

1. **Модель** (`model.ts`) не импортирует DOM, `fetch`, `window`. Всё внешнее приходит параметрами (`Api`, другие модели).
2. **Представление** получает модель и *утиные* «порты» (маленькие интерфейсы: `Ui`, `openStore()` …), а не обращается к глобальным функциям `main.ts`. Так его можно заменить компонентом, не трогая модель.
3. Зависимости между фичами — через интерфейсы моделей/портов, не через общие переменные модуля.
4. Новая фича — сразу в `features/<имя>/` по этой схеме; при правке старого кода из `main.ts` стоит выносить его туда же.

## Переход на фреймворк (как это выглядит)

Для каждой фичи пишется компонент, который читает `model` (`useSyncExternalStore(model.subscribe, model.get)` в React,
`$model` в Svelte) и вызывает его действия; `model.ts` остаётся без изменений вместе с тестами. Старое `view.ts` удаляется.
Переносить можно по одной фиче: ванильные и фреймворк-представления спокойно живут вместе.

## Что уже вынесено

- `editor` — центральная модель: layouts/sources/plugins, рабочая копия layout, выбор, «несохранённое», история (undo/redo), загрузка, сохранение, слои, операции над layout. Каждое изменение приходит с `change: ChangeKind`, по нему `main.ts` решает, что перерисовать. Рабочая копия правится на месте (жесты на канвасе меняют transform каждый кадр); `main.ts` держит только читаемое «зеркало» состояния.
- `layers`, `layouts` — панели слоёв и layout'ов: чистые функции строк (`model.ts`) и вид (`view.ts`) над портами `editor`.
- `properties` — панель свойств: поля трансформации и обрезки, источник (имя, адрес, прокси), настройки layout; `plugin-settings` — форма настроек плагина по схеме из plugin.json.
- `add-source` — диалог Add Source (iframe, существующий источник, плагин).
- `copy` — копирование слоя между layout'ами и буфер Ctrl+C/V.
- `keyboard` — сопоставление клавиш и контекста с командами (`main.ts` исполняет команды); `live` — обработка сообщений WebSocket через порты, сокет с переподключением.
- `history` — панель «History» (🕘 в шапке): шаги правок с подписями («Move Chat», «Hide Alerts»…), переход к любому шагу как в FL Studio; логика — `History` в `shared/history.ts` и `editor.jumpTo`.
- `canvas` — рамки, ручки и pointer-события канваса (DOM); математика жестов — в `shared/gestures.ts`.
- `obs-status` — бейджи «OBS: …» и «scene: …»; `lib/toast.ts` — всплывающие сообщения.
- `view-prefs` — режим компоновки и прилипание (флаги в localStorage через порт).
- `store`, `app`, `config`, `twitch`, `devices`, `obs-import`, `scene-binding`, `notifications` — плагины, настройки, OBS, уведомления.
- Инфраструктура `lib/` (store, api, ui, dom) и чистая логика в `web/shared/` (history, snap, geometry, gestures — математика жестов канваса: ресайз, обрезка, поворот, попадание курсора).

## Что НЕ перенесено (`main.ts`, ~470 строк)

Логики в `main.ts` не осталось: это «склейка» — создание моделей и представлений, порты между ними, подписчик перерисовки по `ChangeKind`, несколько однострочных диспетчеров (клавиши → команды). В фреймворке она станет корневым компонентом.

Следующий шаг при желании: компоненты фреймворка по одной фиче поверх существующих `model.ts` (ванильные и фреймворк-представления могут жить вместе).
